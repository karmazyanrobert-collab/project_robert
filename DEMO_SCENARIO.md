# DEMO_SCENARIO: сценарий защиты University Data Platform Demo

## Цель демонстрации

Показать автономную Data Platform для университета, которая запускается в Streamlit Cloud без Docker, локальных команд и внешних сервисов. Все enterprise-компоненты представлены рабочими локальными аналогами.

## Перед началом

Откройте приложение Streamlit Cloud с entrypoint `dashboard/app.py`. Если warehouse отсутствует, dashboard автоматически создаст данные, слои Lakehouse и DuckDB. Это важно проговорить: пользователь не запускает pipeline руками в терминале.

## 1. Открыть dashboard

**Что нажимать:** ничего, просто открыть ссылку Streamlit Cloud.

**Что говорить:**

> Приложение полностью автономное. При первом открытии оно проверяет наличие `data/warehouse.duckdb`. Если файла нет, запускается встроенный Python pipeline, который генерирует данные и строит все слои платформы.

## 2. Показать архитектурную схему

**Где:** вкладка **Обзор**, раздел **Архитектура платформы**.

**Что говорить:**

> Данные идут от источников в Bronze, затем проходят Data Quality, очищаются в Silver, агрегируются в Gold, используются в Feature Store, загружаются в DuckDB Warehouse, читаются Semantic Layer и отображаются в Streamlit Dashboard.

Покажите таблицу соответствия компонентов задания и реализации.

## 3. Показать запуск / пересоздание пайплайна

**Что нажимать:** кнопка **Запустить / пересоздать пайплайн** в sidebar.

**Что говорить:**

> Это локальная замена Airflow/Prefect. В демо нет отдельного scheduler, потому что Streamlit Cloud должен запуститься одной ссылкой. Pipeline пересоздаёт source data, Bronze/Silver/Gold parquet и DuckDB warehouse.

## 4. Показать Lakehouse Bronze/Silver/Gold

**Где:** вкладка **Lakehouse**.

**Что говорить:**

> Lakehouse реализован через parquet-слои `data/bronze`, `data/silver`, `data/gold` и DuckDB. Bronze хранит сырые данные, Silver — очищенные, Gold — бизнес-витрины. Таблица файлов показывает реальные parquet-файлы и количество строк.

Покажите lineage-таблицу: students, grades, assignments, LMS и room events проходят путь до Gold-витрин.

## 5. Показать Data Quality Report

**Где:** вкладка **Качество данных**.

**Что говорить:**

> FAIL здесь не означает поломку проекта. Несколько ошибок специально добавлены в Bronze, чтобы показать контроль качества. Report фиксирует ошибочные строки, а Silver-слой удаляет или исправляет некорректные данные.

Покажите метрики: всего проверок, пройдено, ошибок обнаружено, доля успешных проверок.

## 6. Объяснить, почему есть FAIL в Bronze

**Что говорить:**

> В сырых данных могут быть некорректные оценки, нереалистичная длительность LMS-сессии или аудитория с нулевой вместимостью. Это типичная ситуация для enterprise data platform. Важно не скрыть ошибку, а зафиксировать её и не пустить плохие данные в аналитику.

Покажите блок **Что произошло после Data Quality** с разницей Bronze rows и Silver rows.

## 7. Показать Gold-витрины

**Где:** вкладки **Обзор**, **Lakehouse**, **Drill-down аналитика**.

**Что говорить:**

> Gold-витрины уже подготовлены для бизнес-потребителей: успеваемость студентов, факультетов, групп, вовлечённость LMS, загрузка аудиторий и признаки студентов.

## 8. Показать Feature Store

**Где:** вкладка **Feature Store**.

**Что говорить:**

> Feast в демо заменён таблицей `student_features`. Она содержит признаки `avg_grade`, `completion_rate`, `engagement_score`, `attendance_score` и `risk_flag`. Эти признаки можно использовать для ML или правил раннего предупреждения.

Объясните `risk_flag`: студент в группе риска, если средний балл ниже 60, completion rate ниже 0.6 или вовлечённость низкая.

## 9. Выбрать факультет и группу, показать drill-down

**Что нажимать:** в sidebar выбрать конкретный **Факультет**, затем конкретную **Группу**.

**Что говорить:**

> Фильтры не декоративные. При выборе факультета KPI, таблицы и графики пересчитываются только по этому факультету, а список групп ограничивается его группами. При выборе группы dashboard переходит на уровень студентов.

Покажите блок **Текущий фильтр** и изменение количества студентов после фильтрации.

## 10. Нажать «Сгенерировать потоковые события»

**Что нажимать:** кнопка **Сгенерировать потоковые события** в sidebar.

**Что говорить:**

> Kafka заменена встроенным генератором событий. Он добавляет новые LMS clicks, assignment submissions и building entries в DuckDB. После нажатия обновляются потоковые KPI и таблица последних событий.

## 11. Показать обновление streaming analytics

**Где:** вкладка **Потоковая аналитика**.

**Что говорить:**

> Здесь показаны событий за минуту, активные студенты за последние 5 минут, отправленные задания и входы в корпуса. Date range также влияет на список потоковых событий.

## 12. Объяснить соответствие требованиям задания

**Где:** вкладка **Обзор**, таблица соответствия компонентов.

**Что говорить:**

> Проект намеренно не использует настоящие Kafka, Airflow, Grafana, ClickHouse, MinIO, Feast, Cube.js и Delta Lake, потому что задача — автономный запуск в Streamlit Cloud. Вместо этого есть рабочие локальные аналоги, которые демонстрируют те же архитектурные роли.

## Как объяснить отсутствие Docker

> Docker не используется, потому что Streamlit Cloud запускает Python-приложение напрямую. Все зависимости указаны в `requirements.txt`, а данные генерируются самим dashboard. Это делает демо воспроизводимым для проверяющего: достаточно открыть ссылку.

## Как объяснить отсутствие настоящих Kafka/Airflow/Grafana/Delta Lake

- **Kafka:** заменена генератором событий и таблицами `streaming_events`, `streaming_metrics` в DuckDB.
- **Airflow:** заменён `src/pipeline.py`, который выполняет шаги pipeline последовательно.
- **Grafana:** заменена Streamlit dashboard с KPI, графиками и таблицами.
- **Delta Lake / Iceberg:** заменены Bronze/Silver/Gold parquet-слоями и DuckDB, чтобы сохранить автономность. В production эти слои можно перенести на S3 + Delta/Iceberg.
- **Feast:** заменён таблицей `student_features`.
- **Cube.js:** заменён `src/semantic_layer.py`.
